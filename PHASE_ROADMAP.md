# Bot-Tree phase implementation notes

## Current safe development slice

- **Phase E sizing groundwork:** `bitget_orders.py` reads CCXT market metadata and creates an offline per-level order plan. It accounts for per-order minimum notional, amount precision, contract size, SL/TP geometry, and a hard total-notional cap. If an order minimum is unknown or the budget cannot support it, it rejects the plan.
- **No exchange submission is enabled.** `assert_submission_disabled()` fails closed. This is deliberate until the exact Bitget UTA v3 order schema, demo header/key behavior, TP/SL attachment to resting and partially filled limits, and contract quantity units have been verified with a Demo API Key. Do not set `DRY_RUN=off` expecting this code to place orders.
- **Phase 5:** `signal_engine.py` runs the existing indicator and grid-risk gates without importing/calling an AI provider and writes bot-ready setups to `signal.json`. It keeps all current hard gates (structure, EMA, MACD, near S/R, VWAP, 30m trend, valid grid geometry).
- **Phase 6 reporting:** `paper_metrics.py` summarizes closed trades already in `state.json`. It is read-only and flags the bounded-history and approximate-idle-time limitations. It does not claim that a short sample passes paper criteria.

## Commands

```bash
python tes_bitget_orders.py
python signal_engine.py
python paper_metrics.py
```

`signal_engine.py` reads `daftar_ai.json` (which can be generated by the existing non-AI fallback flow) and writes `signal.json`. The AI flag remains off; this pipeline does not use AI even if another script does.

## Required validation before any demo order

1. Run paper for at least 1–2 weeks and preserve an append-only trade journal beyond the state file's bounded history.
2. Verify net expectancy after realistic fees/slippage, drawdown, sufficient sample size, segment results, and stop limits.
3. Confirm Bitget's current UTA v3 request/response fields from the official documentation and manually inspect the constructed request.
4. Test one small order only in a dedicated demo account, including pending, partial fill, cancel, TP, SL, restart/reconciliation, and network-error cases.
5. Keep live execution disabled until independent review and explicit risk approval.
